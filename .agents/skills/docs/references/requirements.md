# 需求与规格

## 调查和澄清

先只读调查现有行为、相关代码、用户文档和已知约束。按以下顺序处理高影响歧义：

1. 范围、角色和权限边界；
2. 数据、安全、隐私和租户隔离；
3. 核心用户流程与失败恢复；
4. 性能、兼容性、可用性和运维要求；
5. 技术偏好。

只询问会改变方案或造成明显风险的问题。可安全推断的内容写入“假设”，并说明依据。

## PD 中的建议结构

```markdown
# <功能名称>

## 文档信息
- Iteration: `Iter<number>-<Name>`
- Product Design: `PDnnnn-Name`
- Status: `draft | planned | in-progress | complete`

## 背景与目标
## 范围
### 包含
### 不包含
## 角色与用户场景
## 需求
### REQ-001 <单一、可观察的行为>
- 优先级：P1 | P2 | P3
- 验收场景：SC-001
  - Given ...
  - When ...
  - Then ...
## 非功能要求
## 边界与异常
## 假设与依赖
## 待确认项
```

每条需求只表达一个行为，并至少有一个可验证场景。场景描述结果，不指定 Controller、表名、框架或具体类。

PD 定稿时将它添加到 `Demand.md` 的迭代目录；如果包含重要设计决策，同时添加到 `Design.md` 索引。

## 质量清单

- 目标、成功指标、包含范围和排除范围明确；
- 角色、授权、租户和数据归属清楚；
- 正常、空值、重复、冲突、无权限、超时和依赖失败路径按风险覆盖；
- 验收条件具体可测，避免“友好”“快速”“完善”等无度量词；
- 性能、容量、兼容、可访问性、审计和可观测性有需要时可量化；
- 没有实现细节污染需求，也没有 `TODO`、`TBD` 或未登记的隐含决定；
- 每个待确认项说明如果不确认会影响什么。

发现问题时先修订文档再进入设计。需求质量清单通过只代表意图足够清晰，不代表实现完成。
