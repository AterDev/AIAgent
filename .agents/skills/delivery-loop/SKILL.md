# 交付闭环

把当前迭代的 PD 视为意图源，PT 视为计划和实现记录，代码和验证结果视为完成证据。checkbox 只是进度索引，不能单独证明完成。

## 工作模式

- **Implementation mode**：用户要求编码、修复或继续计划时使用。必须更新当前 PT、`ProjectTracking.md` 和受影响 PD。
- **Audit mode**：用户只要求查看进度、审查计划或判定完成时使用。保持只读，报告过时文档和建议修订，不擅自写回。

## 启动

1. 读取适用的 `AGENTS.md`、`Demand.md`、`Design.md` 和 `ProjectTracking.md`。
2. 确认当前 `Iter<number>-Name` 及功能模块，读取其 `PDnnnn-Name.md` 和 `PTnnnn-Name.md`。存在多个候选时只处理用户指定或能从上下文唯一确定的一个。
3. Implementation mode 中没有对应 PT 时，按当前迭代下一个可用四位编号创建简洁 PT；无法确定迭代或 PD 来源时暂停。
4. 建立 `PD/REQ/SC → PT/TASK → 代码 → 验证` 的追踪关系。
5. 先执行只读一致性分析。强制需求无任务覆盖、任务没有来源/完成条件/验证方式、产物矛盾，或存在会改变范围、安全、数据方案的待确认项时，先修订计划。

## 状态语义

- `planned`：已定义但未开始；对应 `- [ ]`。
- `in-progress`：当前正在处理；仍保持 `- [ ]`，在跟踪文档记录当前任务。
- `blocked`：缺少决定、权限、依赖或存在未解决失败；仍保持 `- [ ]` 并记录 blocker。
- `done`：实现和任务要求的验证都已通过；对应 `- [x]`。
- `waived`：经明确决定不执行；不得勾选为完成，记录决定人/原因/影响。

不要用“代码已写”“构建过了”或“测试已添加”替代任务自身的完成条件。

## 执行 loop

重复以下步骤，直到没有 ready task 或出现暂停条件：

1. 选择依赖已完成、优先级最高且范围最小的 pending task。
2. 核对其来源、完成条件和验证方式；确认代码现状没有让任务失效。
3. 实现一个可验证增量。若发现意图错误，先同步需求/设计/任务，不让代码形成未记录的范围漂移。
4. 运行最小充分验证；失败时保留首个有意义错误，诊断原因，修复代码或修订计划后重跑。
5. 在 PT 记录本轮实现结果、代码证据、精确验证命令/结果、未覆盖项和下一步。无论成功、部分成功或阻塞，只要已修改代码就必须记录。
6. 只有完成条件满足且所需验证通过，才把该任务改为 `[x]`。同步 PT 总状态、`done / total` 和 `ProjectTracking.md`。
7. 若改变用户可观察行为、验收条件或设计，同步 PD；只有全局索引/架构受影响时更新 `Demand.md`/`Design.md`，已交付行为再更新 Changelog。
8. 重新计算迭代和项目总进度、剩余 ready task、阻塞项和下一步，再进入下一轮。

可并行任务必须修改不同文件、没有未完成依赖；同一文件和共享迁移按顺序处理。并行分支中的一个失败不应抹掉已验证成功的任务，但必须阻止依赖它的任务。

## 暂停条件

- 任务含义不清或需要扩大已批准范围；
- 实现与需求、设计或项目强制规则冲突；
- 构建/测试失败且原因尚未确定；
- 需要外部权限、凭据、基础设施或用户决定；
- 只能通过弱化断言、跳过检查或隐藏错误来继续。

暂停时记录 blocker、已有证据、影响的任务和解除条件，不把任务标记完成。

## 验证和收敛

实现后执行只读验证：

| 维度 | 检查 |
|---|---|
| Completeness | 所有任务状态、每条强制需求的代码证据、文档和迁移是否齐全 |
| Correctness | 验收场景、边界、失败路径和测试是否证明行为正确 |
| Coherence | 设计决定、项目约定、术语、公开契约和实现是否一致 |

问题分为 `CRITICAL`、`WARNING`、`SUGGESTION`，每条给出来源、代码/文档证据和可执行修复建议。缺少某类产物时明确写“未检查”，不能假装通过。

若发现缺口，Audit mode 只报告建议任务，不修改文档。Implementation mode 在当前 `PTnnnn-Name.md` 末尾追加 `Convergence` 分组和新的单调递增任务 ID：

- 不改写已完成任务来掩盖缺口；
- 新任务回链到需求、场景、设计决定或项目规则；
- 按严重度和依赖排序，再回到执行 loop；
- 没有缺口时保持任务文件不变。

## 完成门槛

仅当以下条件全部满足才声明 `COMPLETE`：

- 所有纳入范围的任务均为 done，或明确记录不影响交付的 waived 项；
- 强制需求和验收场景都有实现与验证证据；
- 必要的 build、test、静态检查、契约/迁移/文档检查已通过；
- 没有 `CRITICAL`，剩余风险已说明；
- 当前 PT 的实现记录、任务/总进度、`ProjectTracking.md` 和受影响 PD 与代码现状一致。

最终摘要只报告状态、`N/M` 进度、本轮完成项、验证证据、阻塞/遗留风险和下一步。测试未运行、环境不具备或证据不足时使用 `INCOMPLETE` 或 `BLOCKED`，不要宣称完成。
